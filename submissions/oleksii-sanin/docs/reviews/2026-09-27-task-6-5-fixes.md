## 1. Correctness

1. lib/transform/ast.ts:96-101 — A list with code in two or more items loses the pairing of step and code. Input: "1. Install:\n\n   ```\n   npm i\n   ```\n\n2. Build:\n\n   ```\n   npm run build\n   ```\n". Output x: ["• Install:\n• Build:\n\n1/3", "```\nnpm i\n```\n\n2/3", "```\nnpm run build\n```\n\n3/3"]. linkedin has the same order. At baea0a0 each command stayed under its step. The ponytail: comment names this ceiling. It reads like a rare case ("text below the code"), but it applies to every list with code in more than one item. The blog output still disagrees, and that disagreement was the motive of 3d1928a. Fix: for each li, emit its text, then its code. The comment already names this upgrade.

2. lib/transform/ast.ts:75 — An item that holds only a code block leaves an empty bullet. That bullet can fill an X part of its own. Input "- ```js\n  const a = 1;\n  ```\n" gives x ["•\n\n1/2", "```\nconst a = 1;\n```\n\n2/2"] and linkedin "• \n\n```\nconst a = 1;\n```". Input "- Install\n- ```sh\n  npm i\n  ```\n- Run\n" gives part 1 "• Install\n• \n• Run". 3d1928a introduced this. At baea0a0 the item read "• npm i". Fix: in listText, skip an li whose proseOf is empty. Add a test for it.

3. lib/transform/x.ts:55 — X drops the leading blank lines of a code block. The ternary current ? … : line treats an empty first line as "no line yet". Input "```\n\nfoo\nbar\n```\n" gives x ["```\nfoo\nbar\n```\n\n1/1"]. linkedin keeps the blank line, so the two outputs disagree. 3680dad introduced this: at baea0a0 a code block that fit went to push() whole. Fix: mark "no piece yet" with a flag or with undefined, not with "".

4. lib/transform/x.ts:67 — The "\n" between two lines can land at the edge of a grapheme piece. The fenced part then holds a blank line that the source does not hold. Input "```\n" + "y".repeat(267) + "\n" + "y".repeat(300) + "\n```\n": the body of part 2 is "```\n\n" + "y".repeat(266) + "\n```". With a first line of 266, the body of part 1 ends "\n\n```". Fix: drop one leading or trailing "\n" from each piece of the grapheme split.

5. lib/transform/x.ts:61 — A whitespace-only line at a piece boundary becomes a part that holds only fences. That is the symptom of finding 1.3. Input "```\n" + "y".repeat(267) + "\n   \n" + "y".repeat(265) + "\n```\n" gives 3 parts, and part 2 is "```\n   \n```\n\n2/3". At baea0a0 the same input gave 2 parts. The next line must be 264 to 267 graphemes, so the trigger is rare. Fix: push current only when current.trim() is not empty.

6. lib/transform/ast.ts:92 — The bare-link filter misses two forms, so the URL still prints twice. "- <https://example.com/a>\n" gives linkedin "• https://example.com/a\nhttps://example.com/a", because the line also holds the bullet. "<https://example.com/ä>\n" gives "https://example.com/ä\nhttps://example.com/%C3%A4", because the href is percent-encoded. Fix: remove a leading "• " from each line before the comparison. Also compare with decodeURI(url).

## 4. Spec drift

12. lib/transform/x.ts:65-69 vs spec.md "A code block longer than one part SHALL split at a line end." — The code cuts inside a line even when a line end is available. "```\nshort\n" + "y".repeat(300) + "\n```\n" gives a part 1 body of "```\nshort\n" + "y".repeat(261) + "\n```". A cut after "short" was possible. A line longer than a part must also cut inside itself, and x.test.ts:148 pins that. The spec has no exemption for it. Fix: add the exemption to the spec, as 54a1e9f did for a word, and name the rule that fills the open part first. Or push the open piece at its line end.

13. lib/transform/ast.ts:92 vs spec.md "Each URL SHALL sit on its own line" (the X sentence from 54a1e9f, and the LinkedIn sentence) — Only the target of a link element moves. A bare URL in prose stays inline: "Visit https://example.com/a today.\n" gives x ["Visit https://example.com/a today.\n\n1/1"]. In a long sentence, such a URL also splits inside itself, although it is shorter than a part. "word ".repeat(50) + "https://example.com/some-long-path-here/and-more now" gives a part 1 that ends "https://example.com/some-" and a part 2 that starts "long-path-here/and-more now". Both defects predate the range. 54a1e9f copied the sentence to X. Fix: narrow the spec to "the target of each link element", or detect bare URLs.
